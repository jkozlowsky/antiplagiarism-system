#### Zasada działania dwuetapowego uwierzytelniania.

Zaimplementowany mechanizm uwierzytelniania wymaga od użytkownika pomyślnego przejścia dwóch etapów weryfikacji tożsamości.

**Etap pierwszy (Podanie poświadczeń logowania):**
1. Użytkownik podaje na froncie aplikacji swoje standardowe i poprawne poświadczenia (login oraz hasło). 
2. System weryfikuje ich poprawność, a także sprawdza, czy konto nie jest zablokowane i czy powiązany z nim adres e-mail został wcześniej zweryfikowany (flaga `isVerified = true`). 
3. Jeśli weryfikacja przebiegnie pomyślnie, uwierzytelnienie nie zostaje jeszcze zakończone. Zamiast tego system generuje jednorazowy kod autoryzacyjny, wysyła go na przypisany do konta adres e-mail i zwraca klientowi odpowiedź HTTP 202 ACCEPTED z komunikatem o wymogu weryfikacji MFA (**mfa.required**).

**Etap drugi (Wprowadzenie jednorazowego kodu - 2FA):**
1. Użytkownik wprowadza otrzymany na skrzynkę e-mail jednorazowy kod. 
2. Kod jest przesyłany do endpoint-u `/auth/check2FA`, gdzie następuje jego weryfikacja. 
3. System sprawdza poprawność kodu oraz jego ważność (limit 5 minut liczony od momentu jego wygenerowania). 
4. Pomyślna weryfikacja skutkuje wygenerowaniem tokenów dostępowych JWT, co definitywnie kończy proces logowania. 
5. W przypadku podania niepoprawnego kodu licznik nieudanych prób logowania zwiększa się, co chroni przed atakami typu Brute Force (limit 3 nieudanych prób).

#### Konfiguracja wysyłania wiadomości e-mail z kodem jednorazowym.

Wysyłanie wiadomości e-mail jest realizowane przy użyciu zewnętrznego serwera SMTP (`smtp-relay.brevo.com`). Parametry dostępowe i konfiguracyjne przekazywane są do środowiska aplikacji backendowej (kontenera Docker) za pośrednictwem zmiennych środowiskowych zdefiniowanych w pliku `.env` oraz wstrzykiwanych za pomocą mechanizmu `secrets` w pliku `docker-compose.yml`.

Samo wysyłanie realizowane jest asynchronicznie przez klasę `EmailService` korzystającą z mechanizmu `JavaMailSender`, co sprawia, że proces logowania nie jest blokowany w oczekiwaniu na komunikację z zewnętrznym serwerem pocztowym:
```java
@Async
public void send2FAuthEmail(String Auth2F, String toAddres, String langCode) {
    String subject = translator.translateForUser("email.2fa.subject", langCode);
    String content = translator.translateForUser("email.2fa.content", langCode, Auth2F);
    sendEmail(toAddres, subject, content);
}
```

#### Mechanizm generowania kodów jednorazowych stosowany przy uwierzytelnieniu użytkowników.

Mechanizm generowania opiera się na komponencie `TwoFactorAuthenticationTokenGenerator`, który wykorzystuje generator liczb pseudolosowych (`SecureRandom`), aby utworzyć 8-cyfrowy kod numeryczny.

W celu zachowania bezpieczeństwa i spełnienia wymagań wygenerowany w postaci jawnej kod jest wysyłany bezpośrednio na e-mail użytkownika, ale nigdy nie trafia do bazy danych w takiej formie. Klasa `AuthService` przekształca ten kod w bezpieczny skrót za pomocą algorytmu szyfrowania określonego w stałych konfiguracyjnych (SHA-256). Odpowiada za to metoda `hashToken()`:

```java
private String hashToken(String token) {
    try {
        MessageDigest digest = MessageDigest.getInstance(OneTimeTokenConsts.HASHING_ALGORITHM);
        byte[] encodedHash = digest.digest(token.getBytes(StandardCharsets.UTF_8));
        return getStringFromByteArray(encodedHash);
    } catch (NoSuchAlgorithmException e) {
        throw new HashEncryptionException("Algorithm " + OneTimeTokenConsts.HASHING_ALGORITHM + " does not exist", e);
    }
}
```

#### Mechanizm zapisujący kod jednorazowy i jego limit czasu w relacyjnej bazie danych.

Zapis kodu odbywa się w ramach encji `OneTimeTokenEnt`, mapowanej na tabelę w relacyjnej bazie danych za pośrednictwem Spring Data JPA. W metodzie `generate2FactorCode` serwisu uwierzytelniającego tworzony jest nowy obiekt reprezentujący kod, do którego przypisywane są odpowiednie atrybuty:

* Wygenerowany wcześniej i zahaszowany skrót kodu.
* Login właściciela konta (nazwa użytkownika).
* Typ tokenu: `OneTimeTokenType.CODE_2FA`.
* Flaga użycia: `isUsed = false`.
* Limit czasu, który ustawiany jest na obecny czas powiększony o 5 minut zdefiniowane w konfiguracji (`LocalDateTime.now().plusMinutes(OneTimeTokenConsts.EXPIRATION_ONE_TIME_TOKEN_MINUTES)`).

Tak skonstruowany obiekt jest persystowany w bazie danych poprzez wywołanie `tokenRepository.saveAndFlush(tokenEnt)`. Przed zapisem nowego kodu system sprawdza, czy dany użytkownik posiada inne, wciąż aktywne tokeny MFA. Jeśli tak – unieważnia je, dbając jednocześnie o zablokowanie możliwości zbyt częstego żądania nowego kodu, co chroni przed atakami typu spam.

#### Mechanizm weryfikacji kodu jednorazowego uwzględniający zgodność kodu wprowadzonego przez użytkownika z wzorcem jak i fakt, że nie upłynął termin dla kodu jednorazowego.

Weryfikacja wpisanego kodu przeprowadzana jest na dwóch osobnych warstwach aplikacji:

1. **Weryfikacja wzorca na warstwie prezentacji (DTO):**
   Obiekt transferowy `Verify2FARequestDTO`, służący do odebrania żądania, posiada wbudowaną walidację Bean Validation. Adnotacja `@Pattern(regexp = "^\\d{8}$")` nakłada ścisły rygor na to, aby dostarczony przez klienta ciąg znaków składał się dokładnie z 8 cyfr. W przypadku niezgodności z wzorcem żądanie jest natychmiast odrzucane z błędem walidacji (obsługiwanym przez `GlobalExceptionHandler`), bez obciążania logiki biznesowej i bazy danych.

2. **Weryfikacja poprawności i terminu ważności (Logika Biznesowa):**
   Gdy żądanie przejdzie walidację DTO, kod trafia do metody `verify2FactorCode` w `AuthService`. Jawny kod przesłany przez użytkownika jest poddawany procesowi haszowania (SHA-256) na podstawie tego samego algorytmu, co przy generowaniu. Następnie do repozytorium wywoływane jest zapytanie, które w sposób jednoczesny sprawdza wszystkie niezbędne warunki ważności:

```java
Optional<OneTimeTokenEnt> tokenOpt = tokenRepository
        .findByTokenValueAndUsernameAndTokenTypeAndIsUsedIsFalseAndExpiresAtAfter(
                hashedToken, login, OneTimeTokenType.CODE_2FA, LocalDateTime.now());
```

Zapytanie to zapewnia, że z bazy zostanie zwrócony rekord tylko wtedy, gdy:
  * Skrót kryptograficzny kodu zgadza się ze skrótem zachowanym w bazie (czyli użytkownik podał poprawny kod).
  * Kod należy do danego użytkownika i jest przeznaczony do podwójnego uwierzytelniania.
  * Kod nie został wcześniej zużyty (`IsUsedIsFalse`).
  * Upływający czas nie przekroczył ustalonego limitu 5 minut (pole `ExpiresAtAfter` upewnia się, że czas wygaśnięcia z bazy danych jest późniejszy niż aktualny czas systemowy).

Jeżeli zapytanie nie odnajdzie odpowiedniego tokenu, rzucany jest wyjątek `OneTimeTokenInvalidException`, a w systemie logowana jest nieudana próba logowania. Jeśli weryfikacja powiedzie się, flaga `isUsed` dla danego rekordu zmieniana jest na `true`, co zapobiega ponownemu użyciu tego samego kodu, po czym użytkownik zyskuje dostęp do systemu.
