#### Zasada działania dwuetapowego uwierzytelniania

Zaimplementowany mechanizm uwierzytelniania wymaga od użytkownika pomyślnego przejścia dwóch etapów weryfikacji tożsamości.

**Etap pierwszy (Podanie poświadczeń logowania):**
1. Użytkownik podaje w aplikacji klienckiej swoje standardowe i poprawne poświadczenia (login oraz hasło).
2. System weryfikuje ich poprawność, a także sprawdza, czy konto nie jest zablokowane i czy powiązany z nim adres e-mail został wcześniej pomyślnie zweryfikowany (flaga `isVerified = true`).
3. Jeśli weryfikacja przebiegnie pomyślnie, system generuje jednorazowy kod autoryzacyjny, asynchronicznie wysyła go na przypisany do konta adres e-mail i zwraca klientowi odpowiedź HTTP 202 ACCEPTED z komunikatem o wymogu przejścia drugiego etapu weryfikacji MFA (`mfa.required`).

**Etap drugi (Weryfikacja jednorazowego kodu z wiadomości e-mail):**
1. Użytkownik, po otrzymaniu 8-cyfrowego kodu autoryzacyjnego na swój adres e-mail, wprowadza go w dedykowanym formularzu logowania.
2. Żądanie trafia na punkt końcowy API `/auth/check2FA`, skąd przekazywane jest do warstwy logiki biznesowej.
3. Wprowadzony przez użytkownika jawny kod jest haszowany i porównywany ze skrótem zachowanym w bazie danych. System weryfikuje jednocześnie, czy od momentu wygenerowania kodu nie minęło więcej niż 5 minut oraz czy kod ten nie został już zużyty.
4. Jeżeli weryfikacja przebiegnie pomyślnie, kod oznaczany jest jako zużyty, a użytkownik otrzymuje wygenerowane tokeny dostępowe sesji (JWT), co kończy proces uwierzytelniania sukcesem.
5. W przypadku podania błędnego kodu lub przekroczenia dopuszczalnego limitu czasu, uwierzytelnienie kończy się niepowodzeniem, a system rejestruje kolejną nieudaną próbę logowania na koncie, co chroni przed atakami typu Brute Force (blokada po 3 nieudanych próbach).

#### Konfiguracja wysyłania wiadomości e-mail z kodem jednorazowym

Wysyłanie wiadomości e-mail realizowane jest przy użyciu zewnętrznego serwera SMTP. Parametry konfiguracyjne serwera pocztowego (w tym adres hosta, port, opcje uwierzytelnienia oraz włączenie bezpiecznego protokołu `STARTTLS`) zdefiniowane są w głównym pliku konfiguracyjnym aplikacji `application.properties`. Z uwagi na dobre praktyki bezpieczeństwa, poufne hasło do skrzynki pocztowej nie jest zapisywane jawnym tekstem w kodzie źródłowym. W środowisku produkcyjnym jest ono dynamicznie wstrzykiwane do kontenera z wykorzystaniem bezpiecznego mechanizmu Docker Secrets.

Za sformułowanie i asynchroniczne wysłanie wiadomości e-mail odpowiada dedykowana klasa `EmailService` korzystająca z wbudowanego interfejsu `JavaMailSender`, dzięki czemu proces logowania użytkownika nie jest w żaden sposób blokowany w oczekiwaniu na odpowiedź zewnętrznego serwera pocztowego:

```java
@Async
public void send2FAuthEmail(String Auth2F, String toAddres, String langCode) {
    String subject = translator.translateForUser("email.2fa.subject", langCode);
    String content = translator.translateForUser("email.2fa.content", langCode, Auth2F);
    sendEmail(toAddres, subject, content);
}
```

### Mechanizm generowania kodów jednorazowych

Mechanizm generowania opiera się na wydzielonym komponencie `TwoFactorAuthenticationTokenGenerator`. Aby zapewnić najwyższy poziom bezpieczeństwa i zagwarantować nieprzewidywalność kodów, zrezygnowano z klasycznego generatora na rzecz klasy `SecureRandom`, dostarczającej kryptograficznie silny generator liczb pseudolosowych. Wartość liczbowa jest odpowiednio skalowana tak, aby zawsze tworzyć dokładnie 8-cyfrowy ciąg.

```java
package pl.lodz.p.it.ssbd2026.ssbd01.common.utils;

import org.springframework.stereotype.Component;
import java.security.SecureRandom;

@Component
public class TwoFactorAuthenticationTokenGenerator {
    public String generate2FAToken() {
        final SecureRandom random = new SecureRandom();
        int code = 10_000_000 + random.nextInt(90_000_000);
        return String.valueOf(code);
    }
}
```
Listing 2.8.2. Komponent służący do bezpiecznego generowania numerycznego kodu 2FA.

Z uwagi na założenia projektowe kod w postaci jawnej jest wysyłany bezpośrednio na e-mail użytkownika, lecz z powodów bezpieczeństwa nie może trafić w takiej formie do bazy danych. Przed persystencją, klasa `AuthService` przekształca wygenerowany kod w kryptograficzny skrót przy użyciu algorytmu `SHA-256` (zdefiniowanego w stałych konfiguracyjnych). Proces ten realizuje poniższa metoda:

```java 
private String hashToken(String token) {
    try {
        MessageDigest digest = MessageDigest.getInstance(OneTimeTokenConsts.HASHING_ALGORITHM);
        byte[] encodedHash = digest.digest(token.getBytes(StandardCharsets.UTF_8));
        return getStringFromByteArray(encodedHash);
    } catch (NoSuchAlgorithmException e) {
        throw new HashEncryptionException("Algorithm " + OneTimeTokenConsts.HASHING_ALGORITHM + " does not exist", e);
    }
}
```

###Mechanizm zapisujący kod jednorazowy i jego limit czasu w relacyjnej bazie danych

Zapis informacji odbywa się w ramach encji `OneTimeTokenEnt`, zarządzanej przez mechanizm Spring Data JPA. Proces przygotowania danych do zapisu realizowany jest w metodzie generate2FactorCode serwisu uwierzytelniającego. Inicjowana jest tam nowa encja, do której aplikacja przypisuje: wygenerowany skrót tokenu, nazwę użytkownika, typ kodu (`CODE_2FA`) oraz flagę jego użycia (`isUsed = false`).

Rygorystyczny, 5-minutowy limit czasu na wprowadzenie kodu egzekwowany jest poprzez pole wygaśnięcia, które obliczane jest w oparciu o czas systemowy aplikacji bezpośrednio w momencie tworzenia obiektu:

```java
OneTimeTokenEnt tokenEnt = new OneTimeTokenEnt();
String twoFactorCode = tokenValueGenerator.generate2FAToken();
postCommitTransactionManager.register(() -> emailService.send2FAuthEmail(twoFactorCode, account.getEmail(), account.getLanguageVersion().getLanguage()));

tokenEnt.setTokenValue(hashToken(twoFactorCode));
tokenEnt.setUsername(account.getLogin());
tokenEnt.setExpiresAt(LocalDateTime.now().plusMinutes(OneTimeTokenConsts.EXPIRATION_ONE_TIME_TOKEN_MINUTES));
tokenEnt.setTokenType(OneTimeTokenType.CODE_2FA);
tokenEnt.setUsed(false);

tokenRepository.saveAndFlush(tokenEnt);
```

### Mechanizm weryfikacji kodu jednorazowego

Weryfikacja wprowadzonego kodu przeprowadzana jest warstwowo:

1. Weryfikacja wzorca na warstwie prezentacji (DTO): Obiekt transferowy odbierający żądanie wykorzystuje walidację Bean Validation. Adnotacja `@Pattern(regexp = "^\\d{8}$")` wymusza, aby dostarczony ciąg znaków stanowił dokładnie 8 cyfr. W przypadku niezgodności z wzorcem żądanie jest natychmiast odrzucane, co zwalnia logikę biznesową z obsługi niepoprawnych zapytań.

2. Weryfikacja poprawności i czasu ważności w logice biznesowej: Po pomyślnej walidacji kontrolera, w metodzie `verify2FactorCode` kod jawny jest powtórnie poddawany procesowi haszowania. Następnie repozytorium wykonuje poniższe zapytanie, weryfikując wszystkie reguły biznesowe jednocześnie:

```java
Optional<OneTimeTokenEnt> tokenOpt = tokenRepository
        .findByTokenValueAndUsernameAndTokenTypeAndIsUsedIsFalseAndExpiresAtAfter(
                hashedToken, login, OneTimeTokenType.CODE_2FA, LocalDateTime.now());
```
Listing 2.8.5. Pobranie z bazy danych rekordu spełniającego rygorystyczne warunki ważności.

Zastosowane zapytanie zapewnia wyciągnięcie rekordu tylko i wyłącznie, gdy:

* Skrót kryptograficzny kodu w pełni zgadza się ze skrótem zachowanym w bazie.

* Kod jest przypisany do konta logującego się użytkownika i posiada cel `CODE_2FA`.

* Flaga zużycia wciąż wskazuje na kod aktywny (`IsUsedIsFalse`).

* Określony podczas generowania termin nie wygasł (pole `ExpiresAtAfter` jest późniejsze niż obecny czas `LocalDateTime.now()`).

Jeżeli zapytanie nie zwróci rekordu (błędny kod lub upłynięcie 5 minut), rzucany jest wyjątek systemowy, a próba logowania klasyfikowana jest jako nieudana. Jeśli natomiast weryfikacja powiedzie się, flaga `isUsed` na pobranej encji zmieniana jest na wartość true, a stan jest natychmiastowo utrwalany w bazie danych. Takie działanie całkowicie uniemożliwia ponowne wykorzystanie kodu i chroni przed atakami powtórzeniowymi (Replay Attack). Następnie serwer zeruje błędne logowania i autoryzuje użytkownika:

```java
tokenEntity.setUsed(true);
tokenRepository.saveAndFlush(tokenEntity);

return handleSuccessfulLogin(account, ipAddress, langHeader);
```
