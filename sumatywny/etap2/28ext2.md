#### Konfiguracja środowiska deweloperskiego (Docker Compose)

Opis usług i mechanizm sprawdzania stanu :

Aby zapewnić stabilne uruchomienie całego systemu i uniknąć błędów związanych z próbą łączenia się do niegotowych jeszcze serwisów, zastosowano mechanizmy healthcheck oraz dyrektywę depends_on z warunkiem condition: service_healthy. Łańcuch uruchamiania aplikacji wygląda następująco:

* **db**: Usługa bazodanowa uruchamiana z oficjalnego obrazu postgres:18.3. Jej stan (healthcheck) jest sprawdzany za pomocą natywnego polecenia pg_isready, co gwarantuje, że baza jest w pełni gotowa do przyjmowania połączeń. Inicjalizacja schematu odbywa się z wykorzystaniem pliku `init-db.sh`.

* **backend** oraz frontend: Obie usługi budowane są lokalnie ze źródeł (build: context: ...). Kontener backend posiada zależność od db - nie rozpocznie swojego uruchamiania, dopóki baza danych nie zgłosi statusu "healthy". Stan samego backendu jest z kolei weryfikowany poprzez endpoint Spring Actuatora (/actuator/health). Frontend sprawdza swój status za pomocą narzędzia curl. Parametry konfiguracyjne (w tym poświadczenia) są wstrzykiwane w bezpieczny sposób za pomocą mechanizmu secrets.

* **proxy**: Serwer odwrotnego proxy (reverse proxy) stanowi punkt wejścia do aplikacji. Dzięki zastosowaniu zależności depends_on, kontener ten czeka na pełne uruchomienie usług frontend oraz backend, zanim zacznie przekierowywać do nich ruch na portach 80 i 443.

#### Infrastruktura testowa z wykorzystaniem Testcontainers

Środowisko testowe zostało skonfigurowane z wykorzystaniem Testcontainers działając na obrazie relacyjnej bazy danych PostgreSQL w wersji 18.3. Środowisko z wykorzystaniem kontenerów ma na celu umożliwienie testowania aplikacji bez potrzeby rzeczywistego wdrażania aplikacji na serwer produkcyjny. Sama procedura testowania opisana jest szerzej w rozdziale 2.7, gdzie między innymi znajduje się też udokumentowana konfiguracja RestAssured. Przygotowane testy są połączone również z rozszerzeniem S2_MOCK. Każdy z testów dziedziczy po `BaseTestSetup`, gdzie połączone jest uruchamianie Testcontainers z pozostałą konfiguracją testową z wykorzystaniem RestAssured. Sama klasa konfiguracyjna konteneru testowego `TestContainersSetupInit` wygląda następująco, na początku znajduje się funkcja do wczytywania danych z plików "secrets", która ma na celu umożliwić odczyt parametrów w celu dalszego ich wykorzystania.

```java
 private static String readSecret(String filePath) {
        try {
            return Files.readString(Paths.get(filePath)).trim();
        } catch (Exception e) {
            throw new RuntimeException("Nie można odczytać pliku z hasłem: " + filePath, e);
        }
    }
```

Następnie znajduje się sama konfiguracja kontenera, wybieramy odpowiedni obraz bazy danych i wprowadzamy wcześniej zdefiniowane i odczytane poświadczenia.

```java
public static final PostgreSQLContainer<?> postgreSQLContainer = new PostgreSQLContainer<>("postgres:18.3")
```

#### Zgodność środowiska testowego z deweloperskim

Konfiguracja środowiska testowego opartego na Testcontainers wykazuje pełną zgodność ze zdefiniowanym wyżej środowiskiem deweloperskim:

* Oba środowiska wykorzystują dokładnie ten sam bazowy obraz silnika relacyjnej bazy danych: postgres:18.3.

* Zarówno docker-compose, jak i klasa TestContainersSetupInit korzystają z tych samych plików secrets (np. `secrets/pg_password.txt`, `secrets/mok_password.txt`) do konfiguracji poświadczeń, co zapobiega rozbieżnościom w hasłach pomiędzy środowiskami.

* Skrypt `init-db.sh` wykorzystywany w kontenerze deweloperskim posiada swój odpowiednik w środowisku testowym w postaci instrukcji wykonywanych dynamicznie wewnątrz kontenera (`postgreSQLContainer.execInContainer(...)`), co gwarantuje istnienie wymaganych ról dostępowych (modułu MOK) zanim aplikacja w trybie testowym nawiąże połączenie. Zmienne konfiguracyjne Spring Boota dla bazy Testcontainers są dynamicznie nadpisywane przez DynamicPropertyRegistry, odzwierciedlając zmienne środowiskowe z pliku compose.

```java
public class NEG01_unblockUserAccountTest extends BaseTestSetup {
    @Autowired
    private RequestFunctions requestFunctions;

    @Autowired
    private AccountRepository accountRepository;

    @MockitoBean
    private EmailService emailService;

    @Autowired
    private VersionHashService versionHashService;

    @Autowired
    @Qualifier("mokTransactionManager")
    private PlatformTransactionManager transactionManager;

    @BeforeEach
    public void setup() {
        System.out.print("\n\n\n" +
                "Test NEG01_unblockUserAccount\n" +
                "Check if unblocking user account is working properly - unblocking currently unblocked account leads to an error\"\n\n\n");
    }

    @Test
    @DisplayName("Check if unblocking user account is working properly")
    public void NEG01_unblockUserAccountTest() {
        TransactionTemplate transTemp = new TransactionTemplate(transactionManager);
        
        Account testAccount = transTemp.execute(status -> {
            Account adminUser = accountRepository.findByLogin("admin").get();
            LanguageDict ld = adminUser.getLanguageVersion();

            Account account = new Account();
            account.setName("Tester");
            account.setSurname("Surname");
            account.setEmail("mok5@testerneg.com");
            account.setLogin("mok5testerneg");
            account.setIsBlocked(false);
            account.setLanguageVersion(ld);
            account.setPasswordHash("testcontainers_hash");

            return accountRepository.saveAndFlush(account);
        });

        String validHash = versionHashService.hashObjectVersion(testAccount.getId(), testAccount.getVersion());

        String responseBody = requestFunctions.sendPostRequest(
                "",
                409,
                ACCOUNT_UNBLOCK.getKeyName().replace("id", testAccount.getId().toString()),
                new Headers(new Header("If-Match", validHash))
        );

        transTemp.execute(status -> {
            Account accountToUnblock = accountRepository.findById(testAccount.getId()).get();

            assertAll(
                    () -> assertFalse(accountToUnblock.getIsBlocked(), "Assert that account is unblocked"),
                    () -> assertEquals("Account is not blocked", responseBody, "Assert that correct error message is returned")
            );
            return null;
        });
    }
}
```

### Zastosowanie zaślepiania (mocking) dla testowanych komponentów / dostarczanie alternatywnej konfiguracji testowej (3)(S2_MOCK)(MKw)

Osoby realizujące:
* Paweł Rajnert
* Danylo Dobrianskyi
* Jan Kozłowski

Z uwagi na wykorzystanie w pliku `pom.xml` zależności `spring-boot-starter-test` w projekcie możemy rozpocząć korzystanie z Mockito:

```bash
 		<dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
```

W celu wstrzyknięcia atrapy (mocka) do istniejącego komponentu aplikacji podczas testów integracyjnych należy skorzystać z adnotacji `@MockitoBean`, poniżej przykład:

```java
@MockitoBean
    private EmailService emailService;
```

W przypadku testów jednostkowych, stosuje się adnotacje `@Mock` dla utworzenia atrapy oraz `@InjectMock` dla utworzenia atrapy komponentu, który będziemy testowali. Klasa testowa jest wtedy oznaczona przez adnotację `@ExtendWith(MockitoExtension.class)`, przykład poniżej:

```java
@ExtendWith(MockitoExtension.class)
public class AccountServiceBlockAccountTest {

    @Mock
    private AccountRepository accountRepository;

    @Mock
    private EmailService emailService;

    @Mock
    private VersionHashService versionHashService;

    @Mock
    private MokRefreshRepository mokRefreshRepository;

    @Mock
    private PostCommitTransactionManager postCommitTransactionManager;

    @InjectMocks
    private AccountService accountService;
```

W celu oprogramowania atrapy (mocka) należy skorzystać ze słów kluczowych np:
- when, należy opisać jak mock ma się zachować w danej sytuacji jeśli coś się wydarzy,
- verify, weryfikujemy czy działanie poszło zgodnie z planem (jest to taki odpowiednik przykładowo assertTrue).

`ArgumentCaptor` pozwala przechwycić argument przekazany do metody mocka podczas jej wywołania, 
a następnie użyć go w dalszej części testu. Jest to szczególnie przydatne gdy testowana metoda generuje wartość 
wewnętrznie (w naszym przypadku treść wiadomości email) i przekazuje ją do innego komponentu.
Bez captora nie byłoby możliwości odczytania tej wartości z zewnątrz.

```java
@Test
    void POS02_confirmReset_ShouldReturn200_WhenTokenAndHashAreValid() throws Exception {
        String testEmail = commonFunctions.generateRandomEmail();
        createActiveAccount(testEmail, commonFunctions.generateRandomStringOfLength(10));
//        Mockito.reset(emailService);
        ResetPasswordDTO requestDto = new ResetPasswordDTO(testEmail);
        requestFunctions.sendPostRequest(
                objectMapper.writeValueAsString(requestDto),
                200,
                "/api/auth/reset/request",
                new Headers()
        );

        ArgumentCaptor<String> emailBodyCaptor = ArgumentCaptor.forClass(String.class);
        verify(emailService).sendResetPasswordEmail(eq(testEmail), emailBodyCaptor.capture(), any());


        String rawToken = emailBodyCaptor.getValue();

        ConfirmResetDto confirmDto = new ConfirmResetDto(rawToken, "new_secure_passworD123.");
        String responseBody = requestFunctions.sendPostRequest(
                objectMapper.writeValueAsString(confirmDto),
                200,
                "/api/auth/reset/confirm",
                new Headers()
        );
        assertEquals("Password successfully changed.", responseBody);
    }
```
Wywołanie`emailBodyCaptor.capture()` instruuje Mockito, aby podczas weryfikacji wywołania zapamiętał wartość 
drugiego argumentu, którym jest token. Metoda `emailBodyCaptor.getValue()` zwraca następnie ten przechwycony argument, 
który w normalnych warunkach trafiłby do skrzynki e-mail użytkownika. Dzięki temu możliwe jest użycie go w kolejnym 
kroku testu tj. żądaniu potwierdzenia resetu hasła bez konieczności wyszukiwania tokenu bezpośrednio w bazie danych 
ani modyfikowania kodu produkcyjnego.
