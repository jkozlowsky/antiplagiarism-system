#### Sposób uruchomienia i konfiguracji narzędzia do CI/CD oraz zapewnienie trwałości

Do zbudowania infrastruktury i procesu dla CI/CD wykorzystano platformę GitLab CI/CD zintegrowaną z dedykowanymi programami uruchamiającymi GitLab Runner. Uruchomiono je na maszynie wirtualnej w infrastrukturze oVirt.

W celu zapewnienia trwałości konfiguracji oraz niezawodności środowiska, GitLab Runner został skonfigurowany jako usługa systemowa, co gwarantuje jego automatyczny rozruch po restarcie maszyny produkcyjnej.

Proces instalacji i trwałej rejestracji runnera przebiegał następująco:
1. Instalacja Gitlab Runnera

`sudo dnf install gitlab-runner`

2. Rejestracja dedykowanych instancji. Skonfigurowano dwa oddzielne środowiska uruchomieniowe (dla API oraz dla WEB) w trybie shell:

`sudo gitlab-runner register`

Podczas rejestracji nadano tagi `ovirt-runner`, które pozwalają GitLabowi na poprawne kierowanie zadań potoku.

Runner w trybie shell umożliwia bezpośrednie wykonywanie poleceń systemowych na maszynie produkcyjnej. Z kolei etapy testowania i budowania obrazów w potokach wykorzystują izolowane kontenery dzięki technologii Docker-in-Docker (DinD), eliminując potrzebę instalowania środowisk takich jak Node.js czy Maven bezpośrednio na maszynie produkcyjnej.

Zoptymalizowano również plik konfiguracyjny /etc/gitlab-runner/config.toml, ustalając globalny parametr współbieżności concurrent = 4 oraz po request_concurrency = 2 dla każdego z runnerów ("oVirt Runner - API" oraz "oVirt Runner - WEB"), co umożliwia równoległe przetwarzanie zadań z zachowaniem odpowiedniej wydajności serwera.

#### Konfiguracja potoku procesu budowy i wdrożenia

Proces CI/CD został w pełni zautomatyzowany poprzez deklaratywne pliki konfiguracyjne .gitlab-ci.yml umieszczone bezpośrednio w repozytoriach kodu (osobno dla części backendowej (api) i frontendowej (web)).

Wszystkie wrażliwe dane, takie jak hasła do baz danych (np. `$CI_PG_PASSWORD`), identyfikatory (`$CI_GOOGLE_CLIENT_ID`) oraz hasła do rejestru (`$CI_REGISTRY_PASSWORD`), zostały ukryte i skonfigurowane w sposób bezpieczny jako zmienne środowiskowe CI/CD w ustawieniach potoku na GitLabie.

##### Potok dla części serwerowej (Backend - API)

```yaml
stages:
  - test
  - build
  - deploy

test-backend:
  stage: test
  image: maven:3.9.14-eclipse-temurin-25-alpine
  services:
    - docker:29.4.0-dind
  variables:
    DOCKER_TLS_CERTDIR: ""
    DOCKER_HOST: "tcp://docker:2375"
  script:
    - echo "MAIL_HOST=localhost" >> .env
    - echo "MAIL_PORT=1025" >> .env
    - echo "MAIL_USERNAME=test" >> .env
    - echo "PG_DATABASE=$CI_PG_DATABASE" >> .env
    - echo "PG_USERNAME=$CI_PG_USERNAME" >> .env
    - echo "MOK_USER=$CI_MOK_USER" >> .env
    - echo "MPP_USER=$CI_MPP_USER" >> .env
    - mkdir -p secrets
    - echo "$CI_PG_PASSWORD" > secrets/pg_password.txt
    - echo "$CI_MOK_PASSWORD" > secrets/mok_password.txt
    - echo "$CI_MPP_PASSWORD" > secrets/mpp_password.txt
    - echo "test_mail_password" > secrets/mail_password.txt
    - echo "dummy_test_token" > secrets/gitea_token.txt
    - export GITEA_URL=http://localhost:3000
    - export MAIL_HOST=localhost
    - export MAIL_PORT=1025
    - export MAIL_USERNAME=test
    - export MAIL_PASSWORD=test
    - mvn test

build-backend:
  stage: build
  image: docker:29.4.0
  services:
    - docker:29.4.0-dind
  variables:
    DOCKER_TLS_CERTDIR: ""
  before_script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY
  script:
    - docker build -t registry.gitlab.com/iitpl/ssbd/2026/01/api:latest .
    - docker push registry.gitlab.com/iitpl/ssbd/2026/01/api:latest
  only:
    - main

deploy-backend:
  stage: deploy
  tags:
    - ovirt-runner
  before_script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY
  script:
    - cd /opt/api
    - git pull origin main
    - export GOOGLE_CLIENT_ID=$CI_GOOGLE_CLIENT_ID
    - docker compose -f docker-compose.prod.yml pull backend
    - docker compose -f docker-compose.prod.yml up -d
  only:
    - main
```

Plik .gitlab-ci.yml w repozytorium API definiuje trzy etapy: test, build oraz deploy.

* Etap Test (Job: test-backend)
  * Wykorzystuje obraz maven:3.9.14-eclipse-temurin-25-alpine. Uruchamiana jest usługa docker:dind. Skrypt dynamicznie generuje niezbędne pliki konfiguracyjne (.env) oraz strukturę katalogów secrets/, do których wstrzykuje sekrety z GitLaba, a następnie wykonuje mvn test.

* Etap Build (Job: build-backend)
  * Wykorzystuje kontener z Dockerem do zbudowania produkcyjnego obrazu na podstawie wieloetapowego pliku Dockerfile. Zbudowany obraz tagowany jest jako latest i bezpiecznie wysyłany do oficjalnego rejestru kontenerów GitLaba (docker push).

* Etap Deploy (Job: deploy-backend) 
  * Wykonywany na runnerze z tagiem ovirt-runner. Loguje się do rejestru obrazów i przechodzi do katalogu /opt/api. Aby zachować bezpieczeństwo, katalog na serwerze ma nadane uprawnienia dla użytkownika systemowego gitlab-runner, a jego zdalne repozytorium jest uwierzytelniane za pomocą dedykowanego tokenu autoryzacyjnego. Skrypt pobiera najnowszą wersję kodu (git pull origin main), wczytuje nowo zbudowany obraz do dockera (docker compose pull backend) i bezprzerwowo restartuje kontener produkcyjny (docker compose up -d).

##### Potok dla części klienckiej (Frontend - WEB)

```yaml
stages:
  - build
  - deploy

build-frontend:
  stage: build
  image: docker:29.4.0
  services:
    - docker:29.4.0-dind
  variables:
    DOCKER_TLS_CERTDIR: ""
  before_script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY
  script:
    - docker build -t registry.gitlab.com/iitpl/ssbd/2026/01/web:latest .
    - docker push registry.gitlab.com/iitpl/ssbd/2026/01/web:latest
  only:
    - main

deploy-frontend:
  stage: deploy
  tags:
    - ovirt-runner
  before_script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" $CI_REGISTRY
  script:
    - cd /opt/api
    - docker compose -f docker-compose.prod.yml pull frontend
    - docker compose -f docker-compose.prod.yml up -d
  only:
    - main
```

Plik .gitlab-ci.yml w repozytorium aplikacji klienckiej składa się z dwóch etapów: build oraz deploy.

* Etap Build (Job: build-frontend)
  * Proces kompilacji, instalacji zależności oraz finalnego budowania statycznych plików produkcyjnych odbywa się całkowicie wewnątrz obrazu kontenerowego (w oparciu o silnik Node.js 22). Rezultat serwowany jest przez serwer Nginx. Gotowy obraz jest deponowany w rejestrze GitLab.

* Etap Deploy (Job: deploy-frontend)
  * Runner przechodzi do wspólnego katalogu /opt/api, używając produkcyjnego pliku docker-compose.prod.yml, gdzie na bieżąco ściąga nową wersję obrazu GUI i podnosi powiązane usługi w sieciach wirtualnych.

#### Rozpoczęcie procesu budowy (Wyzwalanie automatyczne)

Proces ciągłej integracji i wdrażania został w pełni zautomatyzowany w oparciu o architekturę gałęzi. Wyzwalanie poszczególnych etapów zależy od docelowego rozgałęzienia:
* Każdy push do dowolnej gałęzi pobocznej inicjuje jedynie etap testowania, co pozwala na wczesne wykrywanie błędów w kodzie bez ingerencji w środowisko produkcyjne.
* Zdarzenie typu push lub zatwierdzenie Merge Request do głównego rozgałęzienia (main) wyzwala pełny potok: test, build oraz deploy. Kontroluje to dyrektywa only: - main zdefiniowana przy kluczowych etapach wdrażania.

```java
@Configuration  
public class OpenApiConfig {  
  
    @Bean  
    public OpenAPI customOpenAPI() {  
        final String securitySchemeName = "bearerAuth";  
  
        return new OpenAPI()  
                .info(new Info()  
                        .title("SSBD01 API")  
                        .version("1.0")  
                        .description("API documentation for the SSBD01 project"))  
                .addSecurityItem(new SecurityRequirement().addList(securitySchemeName))  
                .components(new Components()  
                        .addSecuritySchemes(securitySchemeName,  
                                new SecurityScheme()  
                                        .name(securitySchemeName)  
                                        .type(SecurityScheme.Type.HTTP)  
                                        .scheme("bearer")  
                                        .bearerFormat("JWT")  
                        ));  
    }  
}
```

#### Kod implementujący całą operację tłumaczenia i zachowania nowej wersji językowej

Do generowania tłumaczeń wykorzystano usługę **Google Cloud Translation API**. Za komunikację z tym interfejsem odpowiada

        Translation translation = translate.translate(
                text,
                Translate.TranslateOption.sourceLanguage(sourceLanguage),
                Translate.TranslateOption.targetLanguage(targetLanguageCode)

    }

Główna logika biznesowa koordynująca tłumaczenie oraz zapis do bazy danych znajduje się w klasie `SubjectDescriptionTranslationService`
w metodzie `translateSubjectDescription`.

```java
@Service
@RequiredArgsConstructor
@MethodCallLogged
@TransactionLogged
@Transactional(propagation = Propagation.REQUIRES_NEW, readOnly = true, transactionManager = "mppTransactionManager")
@Retryable(retryFor = {JpaSystemException.class}, backoff = @Backoff(delayExpression = "${app.retry.backoff}"), maxAttemptsExpression = "${app.retry.maxattempts}")
public class SubjectDescriptionTranslationService {

    private final SubjectRepository subjectRepository;
    private final LanguageDictRepositoryMPP languageDictRepository;
    private final SubjectDescriptionTranslationRepository subjectDescriptionTranslationRepository;
    private final GoogleTranslationService googleTranslationService;

    @MethodCallLogged
    @PreAuthorize("hasAnyAuthority(T(pl.lodz.p.it.ssbd2026.ssbd01.config.consts.AccountConsts).ROLE_TEACHER, T(pl.lodz.p.it.ssbd2026.ssbd01.config.consts.AccountConsts).ROLE_ADMIN)")
    @Transactional(propagation = Propagation.REQUIRES_NEW, readOnly = false, transactionManager = "mppTransactionManager")
    public String translateSubjectDescription(UUID subjectId, String language) {
        Subject subject = subjectRepository.findById(subjectId).orElseThrow(SubjectNotFoundException::new);
        LanguageDict languageDict = languageDictRepository.findByLanguage(language).orElseThrow(LanguageDictNotFoundException::new);

        SubjectDescriptionTranslation subjectDescriptionTranslation = subjectDescriptionTranslationRepository
                .findBySubjectIdAndLanguageDictId(subjectId, languageDict.getId())
                .orElseGet(()->getTranslation(subject, languageDict));

        return subjectDescriptionTranslationRepository.saveAndFlush(subjectDescriptionTranslation).getTranslatedDescription();
    }

    private SubjectDescriptionTranslation getTranslation(Subject subject, LanguageDict language){
        SubjectDescriptionTranslation originalTranslation = subjectDescriptionTranslationRepository
                .findBySubjectIdAndIsOriginalTrue(subject.getId())
                .orElseThrow(OriginalLanguageNotFoundException::new);

        SubjectDescriptionTranslation newTranslation = new SubjectDescriptionTranslation();
        newTranslation.setLanguageDict(language);
        newTranslation.setSubject(subject);
        newTranslation.setIsOriginal(false);

        newTranslation.setTranslatedDescription(googleTranslationService.translateText(
                originalTranslation.getTranslatedDescription(),
                originalTranslation.getLanguageDict().getLanguage(),
                newTranslation.getLanguageDict().getLanguage()
                ));

        return subjectDescriptionTranslationRepository.saveAndFlush(newTranslation);
    }
}
```

Jeżeli dane tłumaczenie nie istnieje w bazie danych, wywoływana jest metoda `getTranslation`, która odnajduje oryginalny 
opis, wywołuje usługę zewnętrzną w celu dokonania tłumaczenia i zapisuje wynikowy obiekt encji do bazy danych.
