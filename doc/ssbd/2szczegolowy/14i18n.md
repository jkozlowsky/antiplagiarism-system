## 14 Wersje językowe interfejsu użytkownika 1 pkt

Mechanizmy internacjonalizacji (i18n) po stronie interfejsu użytkownika opierają się o bibliotekę `i18next`, skonfigurowaną w pliku `i18n.ts`. Określono tam domyślny język, dostępne zasoby tłumaczeń (wczytywane z plików JSON: `en.json`, `pl.json`, `uk.json`) oraz wtyczkę LanguageDetector do detekcji języka z przeglądarki dla ustawienia domyślnej wersji językowej interfejsu użytkownika. Konfigurację zaprezentowano w listingu 14.1.

```TypeScript
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';

import enTranslations from '../locales/en.json';
import plTranslations from '../locales/pl.json';
import ukTranslations from '../locales/uk.json';

i18n
    .use(LanguageDetector)
    .use(initReactI18next)
    .init({
        resources: {
            en: { translation: enTranslations },
            pl: { translation: plTranslations },
            uk: { translation: ukTranslations }
        },
        fallbackLng: 'en',
        interpolation: {
            escapeValue: false
        }
    });

export default i18n;
```

Listing 14.1. Fragment pliku i18n.ts odpowiadający za konfigurację tłumaczeń w aplikacji web.

Wykorzystano także hook `useTranslation()` z biblioteki `i18next` dla lokalizacji tekstu na stronach interfejsu użytkownika. Istnieje także możliwość zmiany preferowanego języka interfejsu użytkownika poprzez wybór odpowiedniej opcji w nagłówku albo na stronie uwierzytelnienia, która nie wiąże się ze zmianą preferowanego języka w encji bazy danych danego użytkownika.

Po stronie serwera preferencje językowe użytkownika są przechowywane w bazie danych. W encji `Account` zaimplementowano relację do encji `LanguageDict`, która zapisywana jest w kolumnie language_version_id. Fragment encji przedstawia listing 14.2.

Informacja o preferencji językowej użytkownika jest przesyłana w nagłówku `Accept-Language` w podczas uwierzytelnienia w systemie. W tej chwili jest zapisywana też do encji konta danego użytkownika w bazie danych.

Przechowywanie wersji językowej przypisanej do konta jest konieczne do obsługi akcji asynchronicznych i powiadomień. Przechowywany język z encji konta użytkownika jest wykorzystywany na przykład w klasie `EmailService`. Zamiast polegać na nagłówkach żądania HTTP, klasa ta korzysta z metody translacji `translateForUser` zdefiniowanej w klasie pomocniczej `Translator` (zaprezentowanej na listingu 14.4), podając wprost kod języka użytkownika do przekształcenia na zlokalizowany temat i treść maila. Przykład tego mechanizmu na podstawie maila aktywacyjnego przedstawiono na listingu 14.3.

```Java
    public void sendActivationReminderEmail(String toAddress, String token, String langCode) {
        String subject = translator.translateForUser("email.activation.reminder.subject", langCode);
        String content = translator.translateForUser("email.activation.reminder.content", langCode, frontendUrl, token);
        sendEmail(toAddress, subject, content);
    }
```

```Java
package pl.lodz.p.it.ssbd2026.ssbd01.config.i18n;  
  
import lombok.RequiredArgsConstructor;  
import org.springframework.context.MessageSource;  
import org.springframework.context.i18n.LocaleContextHolder;  
import org.springframework.stereotype.Component;  
import pl.lodz.p.it.ssbd2026.ssbd01.entities.Account;  
  
import java.util.Locale;  
  
@Component  
@RequiredArgsConstructor  
public class Translator {  
  
    private final MessageSource messageSource;  
  
    public String translate(String key) {  
        return messageSource.getMessage(key, null, LocaleContextHolder.getLocale());  
    }  
  
    public String translate(String key, Object... args) {  
        return messageSource.getMessage(key, args, LocaleContextHolder.getLocale());  
    }  
  
    public String translateForUser(String key, String langCode, Object... args) {  
        Locale locale = (langCode != null) ? Locale.of(langCode.toLowerCase()) : Locale.ENGLISH;  
        return messageSource.getMessage(key, args, locale);  
    }  
}
```

Listing 14.4. Klasa pomocnicza `Translator` która tłumaczy komunikaty na podstawie kontekstu lokalizacji ustawianego przez klasę konfiguracyjną `I18nConfig` albo na podstawie kodu `languageCode` przesyłanego jako argument.

Podobnie zachowuje się system tłumaczenia dla komunikatów błędów API. Za dobór wersji językowej dla wyjątków biznesowych `AppBaseException` oraz błędów walidatora formatu danych (`ConstraintViolationException`) odpowiada klasa `GlobalExceptionHandler`. Jej implementację zaprezentowano na listingu 14.5. Wyjątki logiki `AppBaseException` są tu tłumaczone przez funkcję pomocniczą `translate()` klasy `Translator`, która pobiera bieżący kontekst lokalizacji z nagłówku `Accept-Language` z żądania klienta w klasie konfiguracyjnej `I18nConfig` zaprezentowanej na listingu 14.6.

@RestControllerAdvice
@RequiredArgsConstructor
public class GlobalExceptionHandler {

    private final Translator translator;

    @ExceptionHandler(AppBaseException.class)
    public ResponseEntity<String> handleAppBaseException(AppBaseException exception) {
        String translatedMessage = translator.translate(exception.getReason());
        return ResponseEntity.status(exception.getStatusCode()).body(translatedMessage);

    @ExceptionHandler(ConstraintViolationException.class)

```Java
package pl.lodz.p.it.ssbd2026.ssbd01.config.i18n;  
import org.springframework.context.annotation.Bean;  
import org.springframework.context.annotation.Configuration;  
import org.springframework.web.servlet.LocaleResolver;  
import org.springframework.web.servlet.i18n.AcceptHeaderLocaleResolver;  
  
import java.util.Arrays;  
import java.util.Locale;  
  
@Configuration  
public class I18nConfig {  
  
    @Bean  
    public LocaleResolver localeResolver() {  
        AcceptHeaderLocaleResolver resolver = new AcceptHeaderLocaleResolver();  
        resolver.setDefaultLocale(Locale.ENGLISH);  
        resolver.setSupportedLocales(Arrays.asList(  
                Locale.ENGLISH,  
                Locale.of("pl"),  
                Locale.of("uk")  
        ));  
        return resolver;  
    }  
}
```

Listing 14.6. Klasa konfiguracyjna `i18nConfig`

Z kolei w przypadku błędu walidacji adnotacji modelu, same komunikaty w `violation.getMessage()` są już przetłumaczone przez wbudowane mechanizmy Spring Validation, które też opierają się na analizie nagłówka `Accept-Language` za pomocą domyślnego mechanizmu LocaleResolver powiązanego z danym zapytaniem HTTP. Przykład zastosowania zlokalizowanych komunikatów jest zaprezentowany na listingu 14.7.

```Java
@Data  
@NoArgsConstructor  
public class ChangeOtherPasswordDto {  
  
    @Size(min = 12, message = "{error.password.too.short}")  
    @NotBlank(message = "{error.new.password.blank}")  
    @Pattern(  
            regexp = "^(?=.*[a-z])(?=.*[A-Z])(?=.*\\d).*$",  
            message = "{validation.password.pattern}",  
            groups = OnCreate.class  
    )  
    private String newPassword;  
  
}
```
