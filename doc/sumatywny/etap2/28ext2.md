#### Zasada działania dwuetapowego uwierzytelniania

Zaimplementowany mechanizm uwierzytelniania wymaga od użytkownika pomyślnego przejścia dwóch etapów weryfikacji tożsamości.

**Etap pierwszy (Podanie poświadczeń logowania):**
1. Użytkownik podaje w aplikacji klienckiej swoje standardowe i poprawne poświadczenia (login oraz hasło).
2. System weryfikuje ich poprawność, a także sprawdza, czy konto nie jest zablokowane i czy powiązany z nim adres e-mail został wcześniej pomyślnie zweryfikowany (flaga `isVerified = true`).
3. Jeśli weryfikacja przebiegnie pomyślnie, system generuje jednorazowy kod autoryzacyjny, asynchronicznie wysyła go na przypisany do konta adres e-mail i zwraca klientowi odpowiedź HTTP 202 ACCEPTED z komunikatem o wymogu przejścia drugiego etapu weryfikacji MFA (`mfa.required`).

**Etap drugi (Weryfikacja jednorazowego kodu z wiadomości e-mail):**
1. Użytkownik, po otrzymaniu 8-cyfrowego kodu autoryzacyjnego na swój adres e-mail, wprowadza go w dedykowanym formularzu logowania.
2. Żądanie trafia na punkt końcowy API `/auth/check2FA`, skąd przekazywane jest do warstwy logiki biznesowej.
3. Wprowadzony przez użytkownika jawny kod jest haszowany i porównywany ze skrótem zachowanym w bazie danych. System weryfikuje jednocześnie, czy od momentu wygenerowania kodu nie minęło więcej niż 5 minut oraz czy kod ten nie został już zużyty.
4. Jeżeli weryfikacja przebiegnie pomyślnie, kod oznaczany jest jako zużyty, a użytkownik otrzymuje wygenerowane tokeny dostępowe sesji (JWT), co kończy proces uwierzytelniania sukcesem.
5. W przypadku podania błędnego kodu lub przekroczenia dopuszczalnego limitu czasu, uwierzytelnienie kończy się niepowodzeniem, a system rejestruje kolejną nieudaną próbę logowania na koncie, co chroni przed atakami typu Brute Force (blokada po 3 nieudanych próbach).

#### Konfiguracja wysyłania wiadomości e-mail z kodem jednorazowym

Wysyłanie wiadomości e-mail realizowane jest przy użyciu zewnętrznego serwera SMTP. Parametry konfiguracyjne serwera pocztowego (w tym adres hosta, port, opcje uwierzytelnienia oraz włączenie bezpiecznego protokołu `STARTTLS`) zdefiniowane są w głównym pliku konfiguracyjnym aplikacji `application.properties`. #### Mechanizm generowania kodów jednorazowych

Mechanizm generowania opiera się na wydzielonym komponencie `TwoFactorAuthenticationTokenGenerator`. Aby zapewnić najwyższy poziom bezpieczeństwa i zagwarantować nieprzewidywalność kodów, zrezygnowano z klasycznego generatora na rzecz klasy `SecureRandom`, dostarczającej kryptograficznie silny generator liczb pseudolosowych. Wartość liczbowa jest odpowiednio skalowana tak, aby zawsze tworzyć dokładnie 8-cyfrowy ciąg.

```java
package pl.lodz.p.it.ssbd2026.ssbd01.common.utils;

import org.springframework.stereotype.Component;
import java.security.SecureRandom;

@Component
public class TwoFactorAuthenticationTokenGenerator {
    public String generate2FAToken() {
        final SecureRandom random = new SecureRandom();
        int code = 10_000_000 + random.nextInt(90_000_000);
        return String.valueOf(code);
    }
}
```
Listing 2.8.2. Komponent służący do bezpiecznego generowania numerycznego kodu 2FA.

Z uwagi na założenia projektowe kod w postaci jawnej jest wysyłany bezpośrednio na e-mail użytkownika, lecz z powodów bezpieczeństwa nie może trafić w takiej formie do bazy danych. Przed persystencją, klasa `AuthService` przekształca wygenerowany kod w kryptograficzny skrót przy użyciu algorytmu `SHA-256` (zdefiniowanego w stałych konfiguracyjnych). Proces ten realizuje poniższa metoda:

```java 
private String hashToken(String token) {
    try {
        MessageDigest digest = MessageDigest.getInstance(OneTimeTokenConsts.HASHING_ALGORITHM);
        byte[] encodedHash = digest.digest(token.getBytes(StandardCharsets.UTF_8));
        return getStringFromByteArray(encodedHash);
    } catch (NoSuchAlgorithmException e) {
        throw new HashEncryptionException("Algorithm " + OneTimeTokenConsts.HASHING_ALGORITHM + " does not exist", e);
    }
}
```

#### Mechanizm zapisujący kod jednorazowy i jego limit czasu w relacyjnej bazie danych

Zapis informacji odbywa się w ramach encji `OneTimeTokenEnt`, zarządzanej przez mechanizm Spring Data JPA. Proces przygotowania danych do zapisu realizowany jest w metodzie generate2FactorCode serwisu uwierzytelniającego. Inicjowana jest tam nowa encja, do której aplikacja przypisuje: wygenerowany skrót tokenu, nazwę użytkownika, typ kodu (`CODE_2FA`) oraz flagę jego użycia (`isUsed = false`).

Rygorystyczny, 5-minutowy limit czasu na wprowadzenie kodu egzekwowany jest poprzez pole wygaśnięcia, które obliczane jest w oparciu o czas systemowy aplikacji bezpośrednio w momencie tworzenia obiektu:

```java

String twoFactorCode = tokenValueGenerator.generate2FAToken();
postCommitTransactionManager.register(() -> emailService.send2FAuthEmail(twoFactorCode, account.getEmail(), account.getLanguageVersion().getLanguage()));

tokenEnt.setTokenValue(hashToken(twoFactorCode));
tokenEnt.setUsername(account.getLogin());
tokenEnt.setExpiresAt(LocalDateTime.now().plusMinutes(OneTimeTokenConsts.EXPIRATION_ONE_TIME_TOKEN_MINUTES));
tokenEnt.setTokenType(OneTimeTokenType.CODE_2FA);
tokenEnt.setUsed(false);

tokenRepository.saveAndFlush(tokenEnt);
```

#### Mechanizm weryfikacji kodu jednorazowego

Weryfikacja wprowadzonego kodu przeprowadzana jest warstwowo:

1. Weryfikacja wzorca na warstwie prezentacji (DTO): Obiekt transferowy odbierający żądanie wykorzystuje walidację Bean Validation. Adnotacja `@Pattern(regexp = "^\\d{8}$")` wymusza, aby dostarczony ciąg znaków stanowił dokładnie 8 cyfr. W przypadku niezgodności z wzorcem żądanie jest natychmiast odrzucane, co zwalnia logikę biznesową z obsługi niepoprawnych zapytań.

2. Weryfikacja poprawności i czasu ważności w logice biznesowej: Po pomyślnej walidacji kontrolera, w metodzie `verify2FactorCode` kod jawny jest powtórnie poddawany procesowi haszowania. Następnie repozytorium wykonuje poniższe zapytanie, weryfikując wszystkie reguły biznesowe jednocześnie:

```java
Optional<OneTimeTokenEnt> tokenOpt = tokenRepository
        .findByTokenValueAndUsernameAndTokenTypeAndIsUsedIsFalseAndExpiresAtAfter(
                hashedToken, login, OneTimeTokenType.CODE_2FA, LocalDateTime.now());
```
Listing 2.8.5. Pobranie z bazy danych rekordu spełniającego rygorystyczne warunki ważności.

Zastosowane zapytanie zapewnia wyciągnięcie rekordu tylko i wyłącznie, gdy:

* Skrót kryptograficzny kodu w pełni zgadza się ze skrótem zachowanym w bazie.

* Kod jest przypisany do konta logującego się użytkownika i posiada cel `CODE_2FA`.

* Flaga zużycia wciąż wskazuje na kod aktywny (`IsUsedIsFalse`).

* Określony podczas generowania termin nie wygasł (pole `ExpiresAtAfter` jest późniejsze niż obecny czas `LocalDateTime.now()`).

Jeżeli zapytanie nie zwróci rekordu (błędny kod lub upłynięcie 5 minut), rzucany jest wyjątek systemowy, a próba logowania klasyfikowana jest jako nieudana. Jeśli natomiast weryfikacja powiedzie się, flaga `isUsed` na pobranej encji zmieniana jest na wartość true, a stan jest natychmiastowo utrwalany w bazie danych. Takie działanie całkowicie uniemożliwia ponowne wykorzystanie kodu i chroni przed atakami powtórzeniowymi (Replay Attack). Następnie serwer zeruje błędne logowania i autoryzuje użytkownika:

```java
tokenEntity.setUsed(true);
tokenRepository.saveAndFlush(tokenEntity);

return handleSuccessfulLogin(account, ipAddress, langHeader);
```

    @PreAuthorize("hasAuthority(T(pl.lodz.p.it.ssbd2026.ssbd01.config.consts.AccountConsts).ROLE_ADMIN)")
    @Retryable(retryFor = ConcurrentUpdateException.class)
    @Transactional(propagation = Propagation.REQUIRES_NEW, transactionManager = "mokTransactionManager")
    public void blockUserAccount(UUID id, String versionHash) {
        Account account = accountRepository.findById(id).orElseThrow(AccountNotFoundException::new);

        mokRefreshRepository.refresh(account);
        if (!versionHash.equals(versionHashService.hashObjectVersion(id, account.getVersion()))) {
            throw new ConcurrentUpdateException();
        }

        if (account.getIsBlocked()) {
            throw new AccountIsBlockedException();
        }

        account.setIsBlocked(true);
        accountRepository.saveAndFlush(account);
        postCommitTransactionManager.register(() ->
                emailService.sendAccountIsBlockedInfo(account.getEmail(), account.getLogin(), account.getLanguageVersion().getLanguage()));
    }

* **db**: Usługa bazodanowa uruchamiana z oficjalnego obrazu postgres:18.3. Jej stan (healthcheck) jest sprawdzany za pomocą natywnego polecenia pg_isready, co gwarantuje, że baza jest w pełni gotowa do przyjmowania połączeń. Inicjalizacja schematu odbywa się z wykorzystaniem pliku `init-db.sh`.

* **backend** oraz frontend: Obie usługi budowane są lokalnie ze źródeł (build: context: ...). Kontener backend posiada zależność od db - nie rozpocznie swojego uruchamiania, dopóki baza danych nie zgłosi statusu "healthy". Stan samego backendu jest z kolei weryfikowany poprzez endpoint Spring Actuatora (/actuator/health). Frontend sprawdza swój status za pomocą narzędzia curl. Parametry konfiguracyjne (w tym poświadczenia) są wstrzykiwane w bezpieczny sposób za pomocą mechanizmu secrets.

* **proxy**: Serwer odwrotnego proxy (reverse proxy) stanowi punkt wejścia do aplikacji. Dzięki zastosowaniu zależności depends_on, kontener ten czeka na pełne uruchomienie usług frontend oraz backend, zanim zacznie przekierowywać do nich ruch na portach 80 i 443.

#### Zgodność środowiska testowego z deweloperskim

Konfiguracja środowiska testowego opartego na Testcontainers wykazuje pełną zgodność ze zdefiniowanym wyżej środowiskiem deweloperskim:

* Oba środowiska wykorzystują dokładnie ten sam bazowy obraz silnika relacyjnej bazy danych: postgres:18.3.

* Zarówno docker-compose, jak i klasa TestContainersSetupInit korzystają z tych samych plików secrets (np. `secrets/pg_password.txt`, `secrets/mok_password.txt`) do konfiguracji poświadczeń, co zapobiega rozbieżnościom w hasłach pomiędzy środowiskami.

* Skrypt `init-db.sh` wykorzystywany w kontenerze deweloperskim posiada swój odpowiednik w środowisku testowym w postaci instrukcji wykonywanych dynamicznie wewnątrz kontenera (`postgreSQLContainer.execInContainer(...)`), co gwarantuje istnienie wymaganych ról dostępowych (modułu MOK) zanim aplikacja w trybie testowym nawiąże połączenie. Zmienne konfiguracyjne Spring Boota dla bazy Testcontainers są dynamicznie nadpisywane przez DynamicPropertyRegistry, odzwierciedlając zmienne środowiskowe z pliku compose.

### Implementacja opcjonalnego uwierzytelniania poprzez serwis zewnętrzny w standardzie OAuth (2)(S2_OAUTH)(MKa)

Osoby realizujące:
* Remigiusz Bartczak
* Karol Dawid

#### Zestaw danych pozyskiwanych z serwisu zewnętrznego


Zewnętrznym dostawcą tożsamości zintegrowanym z systemem jest serwis Google. Proces logowania odbywa się w oparciu o wzorzec Token Exchange. Głównym zbiorem danych pozyskiwanym z serwisu Google jest Google ID Token (będący standardowym tokenem JWT), przekazywany przez przeglądarkę klienta do serwera. Z tego tokenu (z jego sekcji Payload), po uprzedniej kryptograficznej weryfikacji podpisu, aplikacja serwerowa wydobywa pojedynczą kluczową informację niezbędną do uwierzytelnienia:
* `email` – zweryfikowany adres poczty elektronicznej użytkownika w domenie Google.


#### Zestaw danych zachowanych w systemie


Logika aplikacji zakłada, że wszelkie dane opisujące konto oraz uprawnienia są przechowywane wewnętrznie, a zewnętrzny dostawca pełni wyłącznie rolę weryfikatora tożsamości. Do skojarzenia konta Google z kontem w systemie wykorzystywana jest encja Account. Elementami zachowanymi w systemie, niezbędnymi do zrealizowania uwierzytelnienia są:
* `email` – unikalny adres e-mail przypisany do konta użytkownika w systemie, służący jako identyfikator korelujący (tzw. klucz złączenia) z danymi od dostawcy zewnętrznego.
* Pola zarządzające stanem konta (np. `isBlocked`, `isVerified`) – warunkujące możliwość pomyślnego logowania.
* Lista przypisanych poziomów dostępu (`accessLevelList`) – na podstawie których budowany jest ostateczny, wewnętrzny token autoryzacyjny systemu.


#### Proces weryfikacji danych prowadzący do uwierzytelnienia


Proces weryfikacji przebiega bezstanowo i odbywa się całkowicie po stronie serwera aplikacji w klasie `AuthService`. Klient przesyła pozyskany od Google token na punkt końcowy `/auth/google`. System wykorzystuje oficjalną bibliotekę **google-api-client** do weryfikacji zgodności podpisu kryptograficznego tokenu z kluczami publicznymi Google oraz zgodności identyfikatora klienta (tzw. Audience).

Jeśli weryfikacja przebiegnie pomyślnie, z tokenu wyciągany jest adres e-mail, za pomocą którego system wyszukuje odpowiadające mu konto w lokalnej bazie danych. Po weryfikacji statusu konta (czy nie jest zablokowane), system generuje własne tokeny dostępowe JWT (Access Token i Refresh Token), identyczne z tymi generowanymi przy standardowym logowaniu (login/hasło). Dzięki temu mechanizm autoryzacji na dalszych etapach działania aplikacji (kontrola dostępu w kontrolerach) opiera się wyłącznie na danych dostarczanych przez nasz system.

```java
    @Transactional(propagation = Propagation.REQUIRES_NEW, transactionManager = "mokTransactionManager")
    public AuthResponseDTO authenticateWithGoogle(String idTokenString, String ipAddress) {
        try {
            GoogleIdTokenVerifier verifier = new GoogleIdTokenVerifier.Builder(new NetHttpTransport(), new GsonFactory())
                    .setAudience(Collections.singletonList(googleClientId))
                    .build();

            GoogleIdToken idToken = verifier.verify(idTokenString);

            if (idToken == null) {
                throw new InvalidCredentialsProvidedException();
            }

            GoogleIdToken.Payload payload = idToken.getPayload();
            String email = payload.getEmail();

            Account account = accountRepository.findByEmail(email)
                    .orElseThrow(AccountNotFoundException::new);

            if (account.getIsBlocked()) {
                throw new AccountIsBlockedException();
            }

            List<String> roles = account.getAccessLevelList().stream()
                    .filter(AccessLevel::getActive)
                    .map(al -> al.getAccessLevelDict().getAccessLevelName())
                    .toList();

            account.setFailedAttempts(0);
            account.setLastSuccessfulLoginIp(ipAddress);
            account.setLastLoginSuccessDateTime(LocalDateTime.now());
            accountRepository.saveAndFlush(account);

            String token = jwtAuthService.generateToken(account.getLogin(), roles);
            String refreshToken = jwtAuthService.generateRefreshToken(account.getLogin(), roles);

            return new AuthResponseDTO(token, refreshToken);

        } catch (Exception e) {
            throw new InvalidCredentialsProvidedException();
        }
    }
```

#### Przebieg komunikacji między kontekstem użytkownika a kontekstem serwera

1. **Poprawne uwierzytelnienie:**
   1. Kontekst użytkownika (frontend) nawiązuje komunikację z serwisem Google, prosząc o autoryzację.
   2. Po udanym zalogowaniu przez interfejs Google frontend otrzymuje od Google ID Token.
   3. Frontend wysyła żądanie HTTP POST na endpoint `/auth/google` w kontekście serwera, przesyłając uzyskany ID Token w ciele żądania.
   4. Serwer weryfikuje podpis u zewnętrznego dostawcy.
   5. Serwer znajduje konto w bazie po adresie e-mail, upewnia się, że nie jest zablokowane, a następnie generuje lokalne tokeny (Access Token, Refresh Token).
   6. Serwer odpowiada kodem HTTP 200 OK, zwracając wygenerowane poświadczenia systemowe do przeglądarki, po czym użytkownik zostaje zalogowany.

2. Próba sfałszowania poświadczeń uzyskanych z serwisu zewnętrznego
(np. atakujący próbuje ręcznie podmienić adres e-mail w ciele JWT zwróconego przez Google na e-mail administratora systemu)
   1. Atakujący modyfikuje sekcję Payload tokenu Google i przesyła spreparowany token do endpointu `/auth/google`.
   2. Kontekst serwera używa klucza publicznego Google do weryfikacji podpisu zaszytego w nagłówku tokenu.
   3. Ponieważ treść tokenu (Payload) została naruszona po podpisaniu go przez Google, funkcja haszująca wykazuje niezgodność sygnatur. Metoda `verifier.verify(idTokenString)` z klas biblioteki weryfikacyjnej zwraca błąd `IllegalArgumentException` lub `null`.
   4. Uwierzytelnienie natychmiast zostaje przerwane, a serwer odrzuca żądanie, zwracając do klienta wyjątek bezpieczeństwa (kod HTTP 401 Unauthorized – u nas przechwytywany jako `InvalidCredentialsProvidedException`). Wewnętrzny stan systemu pozostaje nienaruszony.

3. Próba uwierzytelnienia na podstawie przedawnionych poświadczeń uzyskanych z serwisu zewnętrznego
   1. Atakujący przechwytuje oryginalny, prawidłowy token od serwisu Google, którego zdefiniowany przez dostawcę czas ważności (pole `exp` w Payload) minął i przesyła go na serwer.
   2. Kontekst serwera weryfikuje token, którego podpis kryptograficzny wciąż pozostaje poprawny.
   3. Mechanizm `GoogleIdTokenVerifier` podczas weryfikacji tokenu odczytuje znacznik czasowy zawarty w `exp` (Expiration Time) i porównuje go z aktualnym czasem systemowym serwera.
   4. Wykrywając, że poświadczenie jest przedawnione, weryfikator odrzuca próbę (token nie przechodzi walidacji czasowej).
   5. Następuje rzucenie błędu wewnątrz bloku `try-catch`, co ponownie skutkuje niepowodzeniem całego procesu i zwróceniem klientowi odpowiedzi HTTP 401 Unauthorized (`InvalidCredentialsProvidedException`). System zabezpiecza tym sposobem przed atakami typu Replay Attack.
